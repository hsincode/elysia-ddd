BUN + ELYSIAJS ／ ドメイン駆動設計のテンプレート

elysia-ddd
設計図

カタログ・在庫・注文の 3 つの境界づけられたコンテキストを、1 つのプロセスで動かすモジュラーモノリス。注文と在庫は Saga で確定・却下・取消・期限切れを回し、コンテキスト間のイベントは Transactional Outbox で「集約ごとの順序」と「購読ごとに 1 回」を守って届ける。

01

全体像

コンテキストごとに src/modules/<name>/ と PostgreSQL のスキーマを分け、テーブルの持ち主をはっきりさせている。同期の問い合わせはカタログへの 1 方向だけで、在庫と注文はイベントだけでつながるので、コンテキスト間の依存に循環は無い。

コンテキスト持っているもの他との関係
catalog商品の名前・価格・販売状態、販売数のリードモデル上流。CatalogApi を公開する
inventory商品ごとの在庫、注文ごとの引当の記録カタログを ACL 越しに読み、注文とはイベントでやりとりする
ordering注文とその状態遷移カタログを ACL 越しに読み、在庫とはイベントでやりとりする
02

層と依存の向き

各コンテキストの内側はヘキサゴナル（ポートとアダプター）。依存は外から内への一方向で、test/architecture.test.ts が全ファイルの import を走査して強制する。

層置くものimport してよいもの
domain集約、値オブジェクト、ドメインサービス、イベントの型、リポジトリのインターフェース同じコンテキストの domain と shared/domain だけ。パッケージも Bun も不可
applicationユースケース、クエリのポート、外部に求めることのポート上に加えて application・自分の contract・shared/application
infrastructureDrizzle のリポジトリとクエリ、ACL、イベントの受け口、テーブル定義domain・application・infrastructure、他コンテキストの contract、任意のパッケージ
presentationElysia のルート、HTTP のスキーマ、エラー → ステータスの表domain・application・presentation、elysia と @elysiajs/*
module.tsコンテキスト内の組み立て（呼ぶのは bootstrap.ts だけ）自分のコンテキストのすべて、他コンテキストの contract

domain と application では Date.now()・new Date()・Math.random()・Bun.*・process.* も使えない。時刻と ID は Clock と IdGenerator から受け取るので、テストで時間を進めて期限の境界を突ける。

エラーの扱い

種類表し方HTTP
入力の形が違うElysia（TypeBox）の検証が止める400
業務ルール違反ユースケースが Result の Err で返す表で決める（422・409）
見つからないErr（OrderNotFound など）404
同時更新の衝突ConcurrencyError を投げる（DB のデッドロックも読み替える）409
想定外例外（応答がスキーマに合わない場合を含む）500

業務エラーは RFC 9457 の Problem Details（type: urn:problem:<エラー名>）。エラー名とステータスの対応表に書き漏れると型検査が通らず、Problem Details の予約名（status など）を持つエラーも型で渡せない。

03

注文の状態遷移

注文は受け付けた時点では在庫の確保待ち（placed）。在庫コンテキストの判断で確定か却下になり、確定したものだけが出荷できる。どの状態で何ができるかは ORDER_TRANSITIONS という表 1 つにだけ書き、実行時の判定・操作ごとの状態の型・API が返す「いまできる操作（actions）」をそこから作る。

5 状態 × 5 操作のすべてをドメインのテストが確かめている。表に無い組み合わせは InvalidOrderTransition（HTTP 409）。
状態＼操作confirmrejectexpirecancelship
placed→ confirmed→ rejected→ cancelled→ cancelled409
confirmed409409409→ cancelled→ shipped
shipped409409409409409
cancelled409409409409409
rejected409409409409409

状態ごとに持てる値は判別共用体で分ける。「出荷済みなのに追跡番号が無い」状態は型の上で作れず、DB でも状態ごとの必須列を CHECK 制約で守る。集約は不変で、order.cancel() は自分を書き換えず、新しい Order と OrderCancelled を返す。

集約の規則値
明細の数1〜50 行（価格を引く前に OrderRequest.parse で確かめる）
数量1〜99 の整数。同じ商品は 1 行だけ
合計100 万円まで（ちょうどは可）
在庫の確保を待つ時間15 分。1 ミリ秒前は取り消せず、ちょうどから期限切れ
取消の理由NFC に正規化し、見た目の文字数で 1〜200。改行は可
追跡番号NFKC で全角を半角に、英字を大文字に（「ｊｐ１２３４－５６７８」→「JP1234-5678」）
04

在庫と引当

在庫コンテキストには集約が 2 つある。商品ごとの在庫 StockItem（0 ≤ reserved ≤ onHand ≤ 1,000,000）と、注文ごとの引当の記録 Reservation。記録があるので、イベントが重複しても順番が入れ替わっても、在庫を二重に動かさない。

いまの記録OrderPlaced（引当）OrderCancelled（戻す）OrderShipped（出庫）
無し引き当てるvoided を残す不整合として例外
reserved何もしない（重複）在庫に戻して released在庫から出して fulfilled
rejected ・ voided ・ released何もしない何もしない不整合として例外
fulfilled何もしない不整合として例外何もしない（重複）

「不整合として例外」は、注文の遷移表が許さないので起きないはずの組み合わせ。握りつぶさずに投げ、リトライとデッドレターで人が気づけるようにしている。

ドメインサービス allocate

注文 1 件分の在庫を全部引き当てるか、何も引き当てないかで決める。複数の StockItem にまたがる判断なので、どの集約のメソッドにもできない。同じ商品の行は合算し、一度も入荷していない商品は在庫 0 として扱い、足りなければ不足（商品・求めた数・あった数）をすべて報告する。

1 トランザクションで複数の集約を変えるのは「1 トランザクション 1 集約」から外れるが、注文単位の全部か無しかが業務の要求なので意図して外している。代わりに在庫の行ロックを商品 ID の順に取り、デッドロックを避ける。

対象同時更新への備え理由
注文・商品・引当の記録楽観ロック（version 列）＋読み直し同じ行を同時に触ることがまれ
在庫（StockItem）悲観ロック（FOR UPDATE、商品 ID の順）人気商品に引当が集中する。順番待ちのほうがやり直しの連鎖より速い
05

リクエストの流れ

トランザクションは AsyncLocalStorage に載せ（アンビエントトランザクション）、リポジトリは「いまのトランザクション」を自分で拾う。ユースケースは tx を受け渡さず、UnitOfWork.run だけを知る。Err を返すか例外でロールバックし、入れ子はセーブポイントになる。

06

注文と在庫の Saga

注文の確定には在庫コンテキストの判断が要る。全体を仕切る役（オーケストレーター）は置かず、お互いのイベントに反応して進むコレオグラフィ型にしている。取消は Saga の補償で、引き当てていれば戻し、まだなら「あとから来る引当を断る」記録を残す。

  • 取消・期限切れのあとに届いた「確保できた」は、注文が遷移表で断って無視する。在庫は取消のイベントで戻る。
  • OrderPlaced がデッドレターになって取消だけが届いたときは、在庫が voided を残す。あとで OrderPlaced を手で再開しても引き当てない。
  • 在庫の知らせがいつまでも来ない注文は、15 分で期限切れになる（30 秒ごとの定期ジョブ）。
  • 参加者が 3 者以上になったり、複数段の補償が要るようになったら、注文ごとの進行を持つプロセスマネージャーに切り替える。
07

イベントの配送

集約の変更とイベントを同じトランザクションで outbox に書き、コミット後に OutboxRelay が配送する。メッセージブローカーは使わず、同じ PostgreSQL の上で完結させている。

購読ごとに 1 回

処理と配送済みの記録を同じトランザクションで確定する。同じ DB に書くだけの購読は二重に適用されない。

失敗は巻き込まない

購読ごとのセーブポイントで、失敗した購読の書き込みだけを戻す。成功した購読には二度届けない。

集約ごとの順序

同じ集約の古いイベントが配送待ちなら、新しいものは待つ。ほかの集約は待たせない。

毒メッセージを止める

決めた回数（デフォルト 10）失敗したらデッドレターにして、同じ集約の後続を流す。

複数台で動かせる

FOR UPDATE SKIP LOCKED で 1 件ずつ取り、同じイベントを取り合わない。

太らない

配送済みは 7 日、冪等キーは 24 時間で定期ジョブが消す。

外部のサービスを呼ぶ購読（メール送信など）は DB と同じトランザクションに入れられないので「少なくとも 1 回」になる。受け手の側で重複を捨てられるように作る。購読の名前は配送済みの記録に使うので、運用に乗せたあとは変えない。

10

設計判断

判断・理由・引き換えにしたもの。リポジトリの docs/decisions.md と同じ内容。

1モジュラーモノリスで始め、コンテキストごとに DB のスキーマを分ける
理由
境界は最初から守りたいが、ネットワーク越しの呼び出しと分散トランザクションはまだ要らない。スキーマが分かれていれば、他のテーブルを直接読む近道に気づける。
引き換え
1 つの DB に負荷が集まる。切り出すときは contract と outbox が継ぎ目になる。
2業務エラーは Result、例外は障害だけ
理由
起こりうる失敗が型に出て、HTTP ステータスの表の書き漏れをコンパイルで検出できる。
引き換え
if (!result.ok) return result; が並ぶ。
3集約は不変で、「新しい集約 + イベント」を返す
理由
private なコンストラクタで不正な状態を組み立てさせず、イベントを出し忘れた変更も書けない。
引き換え
パラメータプロパティを使うので erasableSyntaxOnly は有効にできない。
4状態機械は遷移表 1 つから作る
理由
判定・状態の型・API の actions の出どころが 1 か所になり、状態を足しても直す場所がぶれない。
引き換え
型の計算（StateAllowing）が少し込み入る。
5トランザクションは AsyncLocalStorage に載せる
理由
tx をたらい回しにせず、ユースケースの引数を業務の言葉だけにできる。冪等キーのような外側からの包み込みも自然に書ける。
引き換え
トランザクションの中かどうかがコードから見えにくい。リポジトリは必ず db() 経由で触る。
6イベントは Outbox で、集約ごとに順に、購読ごとに 1 回届ける
理由
同じ DB で完結し、「保存したのに消えた」「二重に適用した」が構造的に起きない。順序の保証で受け手が考える組み合わせが減る。
引き換え
ポーリングなので数百ミリ秒遅れる。1 つの集約の失敗は、その集約の後続を止める。
7Saga はコレオグラフィで組む
理由
参加者が 2 者で分岐も 1 つなので、イベントを追えば流れが分かる。
引き換え
流れの全体像がコードの 1 か所に無い。参加者が増えたらプロセスマネージャーに切り替える。
8楽観ロックと悲観ロックを使い分ける
理由
注文は衝突がまれで読み直せばよい。在庫は集中するので順番待ちのほうが速く、ID 順ならデッドロックしない。
引き換え
在庫の引当はロックの間だけ直列になる。
9冪等キーは処理と同じトランザクションで記録する
理由
「処理したのに記録が無い」が起きず、同時送信は一意制約で待たせるだけで済む。
引き換え
外部のサービスを呼ぶ処理には使えない。
10参照はクエリサービスで読む（CQRS-lite）
理由
集約を表示の都合で曲げずに済み、一覧や集計の SQL を自由に書ける。
引き換え
リードモデルは結果整合で、少し遅れる。
11開発とテストは PGlite、本番は Bun.SQL
理由
Docker 無しで動き、SQL もマイグレーションも本番と同じ PostgreSQL の方言。
引き換え
同時実行の性質は実際の PostgreSQL でしか確かめられない。
12ユースケースは関数で、DI コンテナを使わない
理由
デコレーターも reflect-metadata も要らず、テストでは引数を差し替えるだけ。
引き換え
組み立てのコードを自分で書く。
13Elysia は presentation 層に閉じ込める
理由
Elysia 2.0 がベータで、上げるときに触る範囲を限りたい。業務の規則は値オブジェクトに一本化し、HTTP 以外の入口からも同じ規則が効く。
引き換え
OpenAPI に出すため同じ制約を HTTP のスキーマにも書きたくなる。書くなら形にとどめる。

始め方

bun install
bun run dev        # http://localhost:3000 ・ API ドキュメントは /openapi
bun run check      # 型検査 + Biome + テスト

コンテキストを足す手順

  1. src/modules/<name>/ に domain → application → infrastructure → presentation の順で作る。
  2. テーブルは infrastructure/schema.ts に pgSchema("<name>") で定義し、bun run db:generate。
  3. 他のコンテキストに見せるものだけを contract.ts に出す。他を読むときは、自分の application にポートを定義し、infrastructure に ACL を置く。
  4. module.ts で組み立て、src/bootstrap.ts でルートを .use() し、購読を OutboxRelay に、定期ジョブをスケジューラーに渡す。
  5. bun run check。依存の向きを破っていれば test/architecture.test.ts が落ちる。
