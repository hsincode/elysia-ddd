# 設計判断の記録

ADR（Architecture Decision Record）の形で、判断・理由・引き換えにしたものを残す。

## 1. モジュラーモノリスで始め、コンテキストごとに DB のスキーマを分ける

- **判断**: 1 プロセス・1 DB の中に、コンテキストを `src/modules/<name>/` と PostgreSQL のスキーマ（`catalog`・`inventory`・`ordering`）で分けて置く。
- **理由**: 境界は最初から守りたいが、ネットワーク越しの呼び出しと分散トランザクションは、まだ要らない。テーブルの持ち主がスキーマで分かれていれば、他のコンテキストのテーブルを直接読む近道に気づける。
- **引き換え**: 1 つの DB に負荷が集まる。切り出すときは `contract.ts`（同期の API）と outbox（イベント）が継ぎ目になる。

## 2. 業務エラーは Result、例外は障害だけ

- **判断**: ユースケースは `Result<T, E>` を返す。E は `type` を持つ判別共用体。例外はバグ・DB 断・同時更新の衝突だけ。
- **理由**: 起こりうる失敗が型に出る。エラー名 → HTTP ステータスの表に書き漏れるとコンパイルが通らない。
- **引き換え**: `if (!result.ok) return result;` が並ぶ。ライブラリ（Effect など）の力を借りれば短く書けるが、読む人に新しい書き方を覚えさせることになる。

## 3. 集約は不変で、状態を変えると「新しい集約 + イベント」を返す

- **判断**: 集約のコンストラクタは private。`place`・`reconstitute` 以外では作れない。`order.cancel()` は自分を書き換えず、新しい Order と OrderCancelled を返す。
- **理由**: 外から不正な状態を組み立てられない（private なメンバーを持つクラスは、似た形のオブジェクトを代わりに渡せない）。イベントを出し忘れた変更が書けない。
- **引き換え**: パラメータプロパティを使うので、TypeScript の `erasableSyntaxOnly` は有効にできない（Bun は問題なく動かす）。

## 4. 状態機械は遷移表 1 つから作る

- **判断**: `ORDER_TRANSITIONS`（状態 → できる操作）にだけ遷移を書き、実行時の判定、操作ごとの状態の型（`StateAllowing<A>`）、API の `actions` をそこから作る。
- **理由**: 状態が増えたときに直す場所が 1 か所になる。操作の中で「その状態でだけ持つ値」（確定時刻など）を型の上で安全に読める。
- **引き換え**: 型の計算が少し込み入る（`StateAllowing` の定義）。

## 5. トランザクションは AsyncLocalStorage に載せる

- **判断**: 実行中のトランザクションを AsyncLocalStorage に置き、リポジトリは `db()` で拾う。アプリケーション層は `UnitOfWork.run` だけを知る。入れ子はセーブポイント。
- **理由**: tx を引数でたらい回しにしなくてよく、ユースケースの引数が業務の言葉だけになる。冪等キーの記録と処理を同じトランザクションにする、といった外側からの包み込みも自然に書ける。
- **引き換え**: 「いまトランザクションの中か」がコードから見えにくい。リポジトリは必ず `db()` 経由で DB に触ることを守る（PGlite では、トランザクションの外の接続を使うと自分を待って止まる）。

## 6. イベントは Transactional Outbox で、集約ごとに順に、購読ごとに 1 回届ける

- **判断**: イベントは集約と同じトランザクションで outbox に書き、Relay が配送する。同じ集約のイベントは順に届け、購読ごとに配送済みを記録し、決めた回数失敗したらデッドレターにする。
- **理由**: 同じ DB の中で完結するので、「保存したのにイベントが消えた」「二重に適用した」が構造的に起きない。順序の保証があると、受け手が考える組み合わせがぐっと減る。
- **引き換え**: 配送はポーリングなので数百ミリ秒遅れる。1 つの集約の失敗は、その集約の後続を（デッドレターになるまで）止める。

## 7. Saga はコレオグラフィで組む

- **判断**: 注文と在庫はお互いのイベントに反応して進む。全体の進行を持つオーケストレーターは置かない。
- **理由**: 参加者が 2 者で、分岐も 1 つなので、イベントを追えば流れが分かる。補償（取消で在庫を戻す）も、取消のイベント 1 つで済む。
- **引き換え**: 流れの全体像がコードの 1 か所に無い（[messaging.md](messaging.md) の図が頼り）。参加者が増えたらプロセスマネージャーに切り替える。

## 8. 楽観ロックと悲観ロックを使い分ける

- **判断**: 注文・商品・引当の記録は `version` 列の楽観ロック。在庫は `SELECT … FOR UPDATE` を商品 ID の順に取る悲観ロック。
- **理由**: 注文は同じ行を同時に触ることがまれで、衝突したら読み直せばよい。在庫は人気商品に引当が集中するので、やり直しの連鎖より順番待ちのほうが速い。ID の順に取ればデッドロックしない。
- **引き換え**: 在庫の引当はロックを持つあいだ直列になる。極端に集中する商品は、在庫を複数の行に分けるなどの工夫が要る。

## 9. 冪等キーは処理と同じトランザクションで記録する

- **判断**: `Idempotency-Key` の行を処理の前に作り、同じトランザクションの最後に応答を書く。
- **理由**: 「処理したのに記録が無い」「記録だけあって処理していない」が起きない。同じキーの同時送信は一意制約で待たせるだけで済み、処理中を表す状態を持たなくてよい。
- **引き換え**: 冪等キーを使うリクエストは、処理の間ずっとトランザクションを持つ。外部のサービスを呼ぶ処理には使えない（呼んだ事実はロールバックできない）。

## 10. 参照はクエリサービスで読む（CQRS-lite）

- **判断**: 更新は集約とリポジトリ、参照はクエリサービスが表示用の形を直接読む。販売数のような集計は、イベントから作るリードモデルにする。
- **理由**: 集約を「表示に都合のよい形」に曲げずに済む。一覧や集計の SQL を自由に書ける。
- **引き換え**: 同じテーブルを 2 か所（リポジトリとクエリ）から読む。リードモデルは結果整合で、少し遅れる。

## 11. 開発とテストは PGlite、本番は Bun.SQL

- **判断**: `DATABASE_URL` が無ければ PGlite（WASM の PostgreSQL）、あれば Bun.SQL で PostgreSQL に繋ぐ。Drizzle の型はドライバーに依存しない `PgDatabase` にそろえる。
- **理由**: `bun run dev` と `bun test` が Docker 無しで動き、それでいて SQL もマイグレーションも本番と同じ PostgreSQL の方言。
- **引き換え**: PGlite は接続が 1 本なので、同時実行の性質は実際の PostgreSQL でしか確かめられない（そのテストは `TEST_DATABASE_URL` があるときだけ動く）。

## 12. ユースケースは関数で、DI コンテナを使わない

- **判断**: `placeOrder(deps)(input)` のように、依存をクロージャで受ける関数にする。組み立ては `module.ts` と `bootstrap.ts` に手で書く。
- **理由**: デコレーターも reflect-metadata も要らない。テストでは引数を差し替えるだけ。組み立ての誤りは型検査で分かる。
- **引き換え**: 組み立てのコードを自分で書く（コンテキストが 10 を超えるあたりで、組み立ての分け方を考え直す）。

## 13. Elysia は presentation 層に閉じ込める

- **判断**: Elysia を import してよいのは各 `presentation/` と `shared/presentation/` だけ。ドメインの検証は TypeBox ではなく値オブジェクトが行う。
- **理由**: Elysia 2.0 がベータで、上がるときに触る範囲を限りたい。HTTP のスキーマ（形の検証）と業務の規則（値の検証）を分けておくと、ほかの入口（ジョブ・イベント）からも同じ規則が効く。
- **引き換え**: 同じ制約を HTTP のスキーマにも書きたくなる（OpenAPI に出すため）。書くなら「形」にとどめ、業務の規則はドメインに一本化する。
